### 2. Implement FastAPI and persistent incident store

Recommended module layout:

```text
src/cyberheal_investigate/
  __init__.py
  api.py                 # HTTP routes (thin)
  schemas.py             # Pydantic request/response models
  incidents.py           # SQLite transaction store
  sanitize.py            # explicit evidence allow-list
  llm_client.py          # local llama.cpp HTTP client
src/cyberheal_respond/
  __init__.py
  policy.py              # OPA client and decision validator
  approvals.py           # durable approval records
  aws_contain.py         # boto3 test-EC2 quarantine; initially fake
  orchestrator.py        # B -> C adapter
respond/policies/
  cyberheal.rego
  cyberheal_test.rego
```

Suggested endpoints:

| Endpoint | Expected behavior |
|---|---|
| `GET /health` | Simple health check; no credentials |
| `POST /api/v1/alerts` | Validate/sanitize and persist alert; idempotent by incident_id |
| `GET /api/v1/incidents/{id}` | Authenticated incident timeline and status |
| `POST /api/v1/incidents/{id}/investigate` | Produce validated structured explanation |
| `POST /api/v1/incidents/{id}/contain` | Check authenticated operator + OPA allow; fake AWS first |
| `POST /api/v1/incidents/{id}/request-recovery` | Only after approved action; call C contract safely |
| `GET /internal/v1/approvals/{ref}` | Protected, server-to-server approval lookup for C |
| `POST /internal/v1/verification-results` | Authenticated C result ingestion and incident update |

SQLite is enough for the student demo if you enable transactions, unique incident IDs and explicit audit events. Do not expose internal approval lookup publicly. Audit `incident_id`, timestamp, action, scoped resource, policy version/ref, result, snapshot and state changes, with no secrets.

### 3. Evidence sanitization and local LLM (never an authority)

Use an **allow-list** of necessary non-secret features. Remove passwords/tokens/key material, external IPs and raw command output. The local LLM may draft: incident summary, event timeline, likely cause and risk explanation. Strictly validate the parsed result against Pydantic schema; treat it as untrusted text. Use local llama.cpp HTTP server on a laptop with adequate RAM; no cloud GPU is necessary. Mock its outputs in all CI tests and provide deterministic fallback if the LLM is offline. LLM must NOT pick an AWS resource/action from free-text prompts, execute commands or grant permission.

Acceptance tests: malicious prompt in evidence never executes action; missing LLM still yields incident status and clear advisory error; invalid LLM JSON rejected; credentials never appear in model prompts/logs.

### 4. OPA policy: deny by default, incident/resource-bound

Implement a Rego allow-list for the AWS lab. Example inputs:

```json
{
  "subject":{"actor":"approved-demo-operator","roles":["incident-responder"]},
  "action":"quarantine_instance",
  "scope":{"account_id":"123456789012","region":"ap-south-1","lab_tag":"cyberheal-student-lab"},
  "resource":{"vm_id":"i-EXAMPLE","volume_id":"vol-EXAMPLE"},
  "incident_id":"49a29bc4-04ca-4ce7-8ead-2671c970e942"
}
```

Allowed actions for the minimal demo: `quarantine_instance` and `recover_volume` only, on the specific allow-listed test EC2/EBS pair and approved account/Region. Reject unknown actions, resources, roles and missing data. B must call OPA and use an explicit allow. Store the exact evaluated input and returned result in a protected audit record; generate a random opaque approval reference bound to incident/action/scope, TTL and one permitted recovery operation. Do not trust a reference string simply because it is present in a request. Provide OPA policy tests using `opa test` or Docker OPA binary.

B's approval lookup must be authenticated and return **trusted internal data**, not a JSON object copied from the public request. `TrustedRecoveryDecision` in `src/cyberheal_recover/authorization.py` is a verified internal object, NOT a public request model. Return `account_id` (AWS account ID) instead of the old OpenStack `project_id`.

### 5. AWS containment implementation (fake first, then live with account scope)

The AWS equivalent of OpenStack quarantine is **changing an approved EC2 instance's attached Security Group to the lab's no-egress quarantine SG**. The template outputs `test_instance_id`, `security_group_id` and `quarantine_security_group_id`. B must:

1. Look up instance via `DescribeInstances`, verify the instance ID, account, Region and `CyberHealLab` tag; require exactly the allowed network interface arrangement. Never trust public supplied IDs alone.
2. Persist current SG IDs before quarantine for rollback audit. Require explicit OPA allow and authenticated operator.
3. In the mock, record the proposed group change without AWS calls. In live mode, call `modify_instance_attribute(InstanceId=..., Groups=[quarantine_sg_id])` only for the known one-network-interface lab instance. Check the result with `DescribeInstances`. For multiple ENIs use a separate validated design; don't silently apply this function.
4. Record success/failure in SQLite. Repeated action must be idempotent. **Do not auto-unquarantine** when an LLM says so. Final re-entry requires C SAFE and operator decision.
5. Quarantine cuts outbound access including AWS SSM, so the operator must know how to restore the original SG via AWS Console. EC2 Security Groups do not block certain AWS-reserved DNS paths; do not claim complete isolation from all services.
6. Never apply an IAM user disable action to a real credential in a student demo. Use synthetic credential alerts unless a separate test-only IAM identity is explicitly approved.

Use an IAM role limited to test resources/actions with tag-based condition keys where supported. Guard against operators changing the tag to escape restrictions; IAM tag mutation must be separately controlled. Do not use AdministratorAccess for runtime B services.

### 6. B→C recovery handoff — unchanged JSON fields, AWS meaning

B sends `RecoveryRequest` matching `docs/contracts/recovery-request.md`:

```json
{
  "incident_id":"49a29bc4-04ca-4ce7-8ead-2671c970e942",
  "resource":{"vm_id":"i-EXAMPLE","volume_id":"vol-EXAMPLE"},
  "requested_window":{"start":"2026-11-03T00:00:00Z","end":"2026-11-04T08:15:00Z"},
  "opa_decision_ref":"APPROVAL_REF_FROM_PROTECTED_STORE"
}
```

**Additionally, C must obtain via protected internal lookup:** trusted first suspicious timestamp and the OPA allow record bound to `recover_volume`, the AWS account, Region, exact EC2/EBS pair, incident ID, and expiration. Add idempotent job status handling and audit failures. In the minimal setup, B can call C's Python library in-process from an authenticated orchestrator; a separate C HTTP service is unnecessary. C will reject absent/mismatched decision and missing pre-incident verified snapshot.

C returns `VerificationResult` from `docs/contracts/verification.md` with `schema_version=1.0`, incident ID, `rcs`, five factor scores, SAFE/REVIEW/UNSAFE and the selected **EBS `snap-*`** ID. Do not treat SAFE as automatic production service resumption; in the live lab the operator must approve restoration.
